shelf_data.csv 값을 읽어 생성했다. 현재 철제 진열대 설명은 2층, 실행 데이터는 3층이다.
이번에는 수치를 바꾸지 않고 3층까지 후보를 만들었다. 설명과 수치의 최종 일치는 별도 검토가 필요하다.

1~3칸 길이는 모듈을 등각 방향으로 이어 붙였고 쌓기 간격은 후보용 56픽셀이다.
창고는 기존 3종 보관 규칙에 맞춰 윗 덮개와 보관 판 3장을 마련했다.
생성된 판이 부족해서 중간 선반 띠를 등각 기울기에 맞춰 복제하고 발 위치를 유지했다.
복제 부위·기둥·이음새는 실제 맵 연결 전 검토 대상이다.

## 3. 재고 표시 원칙

- 빈 틀에는 고정 상품이 없다. 품절된 칸은 상품 레이어를 그리지 않는다.
- 예시의 sparse는 짝수 슬롯에 물품 1개, 다른 슬롯에는 0개이다.
- full 예시는 진열대 최대 5개, 창고 최대 6개까지 그린다. 실제 수량 자체를 뜻하지 않는다.
- 슬롯은 한 층의 아래/위 판에 번갈아 배치한다. 슬롯 순서·칸 위치·본체 기준점을 JSON에 기록했다.
- 창고는 아래 판부터 서로 다른 물품 최대 3종을 보여 주는 기존 규칙을 기준으로 삼는다.
- 물·약초·철광석·빵·음료는 비교용 재고이다. 플레이어의 시작 물품이나 해금 조건을 바꾸지 않는다.
- 상품을 가리는 뒤판 방향은 빈 본체 그림을 재사용하고 재고 레이어가 없다.
  창고 뒤쪽 가림도 보수적으로 본체만 보여 주며, 교차 지지대와 실제 뒷면 대응은 확인이 남았다.

아이템 81개 중 63개는 기존 실행 아이콘을 줄였다. 나머지 낚시 물품 18개는
items.csv의 icon_path가 비어 있어 받은그림/아이템의 해당 후보를 참조했다.
items.json의 runtime_icon_connected=false로 구분했다. 실행 아이콘 연결까지 완료한 것은 아니다.

## 4. 규격과 보정

- 본체·모듈·상품·상품 레이어는 불투명 색 32개 이하, 합성 예시는 64개 이하이다.
- 모든 개별 PNG는 RGBA, 알파 0/255, 투명 픽셀 RGB=0이다.
- 진열대 모듈은 64×128, 상품 그림은 16×16, 창고는 128×128이다.
- 진열대 본체는 길이와 쌓기에 따라 64~192픽셀 폭·128~320픽셀 높이이다.
- 본체 기준점은 프레임 JSON의 anchor를 사용한다. 3칸 진열대는 아래 여백 40픽셀,
  그 외 본체는 24픽셀이다. 긴 물체 끝이 잘리는 것을 피하기 위한 명시 규격이다.
- 최근접 축소, 알파 160 경계, 디더링 없는 팔레트 축소를 사용했다.
- 같은 상태끼리 본체 기준점과 크기가 같다. 상품 레이어를 합성한 결과가 예시 PNG와 일치한다.

스크립트는 완료된 출력이 있으면 중단한다. --rebuild-draft는 해당 묶음이 아직 Git에
등록되지 않은 초안일 때만 허용한다. 커밋한 후보를 다시 덮어쓰는 용도로 사용할 수 없다.
Pillow와 Windows 맑은 고딕 글꼴을 사용한다. 생성 프롬프트 재실행이 같은 그림을 보장하지 않는다.

## 5. 실제 게임 연결 전에 확인할 것

1. 사용자 선택 후 실행 art/에 복사하고, 현재 2D 전환 코드에 맞는 표시 어댑터를 연결한다.
2. 번호 0~3은 생성 시트의 후보 슬롯이다. 실제 회전 대응과 앞뒤 면은 지도에서 확인해야 한다.
3. 모듈 간 이음새·중간 옆판·쌓기 가림·본체 크기·층 높이를 실제 화면에서 조정한다.
4. 상품은 평면 아이콘을 축소한 후보이다. 판 위치·앞쪽 테두리/기둥 가림·병/빵의 크기를 확인한다.
5. 실제 slots의 item_id/stock을 읽어 상품을 그린다. 예시 PNG를 모든 재고 상태에 붙이면 안 된다.
6. 추가 쌓기·층 제거·보충·품절·회전·보관품 입출고 뒤 그림 갱신과 저장 재개를 확인한다.

이번 묶음은 후보 제작까지의 결과이다. 게임에서 실시간 재고 표시가 동작한다고 검증한 것은 아니다.
실행 코드·씬 변경이 없어 이번 작업에서는 Godot 실행 검사를 새로 수행하지 않았다.
