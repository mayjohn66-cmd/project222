# 공용 이벤트와 계절 이벤트

사용자 결정(2026-10-04): 가게 이벤트를 공용/계절 두 종류로 나누고, 해당 기간에는 특정 물품이 실제로 더 자주 판매되게 한다. 필요한 품목은 소문·생활 이야기와 실제 구매/품절 반응으로 알아차리게 한다.

이 문서는 이전 `콘텐츠_소문에서_진열대로.md`의 일회성 일정·장터 음식 범주 설명을 갱신한다. 소문 → 제조/확보 → 진열 → 계산 → 영업 기록의 흐름은 유지한다. 주민과 상호작용하는 사계절 생활 사건 4개는 별개 콘텐츠이며 완료 답례나 기록을 반복 지급으로 바꾸지 않았다.

## 현재 매장 행사 6개

| 구분 | 행사 | 기간에 더 찾는 상품 | 제조 재료 단서 |
|---|---|---|---|
| 공용 | 던전 공략 채비 | 포션 | 제조법을 안다면 숲 약초·호박 수액·채집한 물 |

- 해당 상품을 손님 구매 후보에 추가 가중치로 넣는다. 기본 수요는 계속 섞이고, 진열·접근·계산이 필요하다. 준비만 하면 전량 팔린다고 보장하지 않는다.
- 봄 장터의 기존 food 범주 수요는 빵/열매 주스 개별 품목으로 바꿨다. 대분류별 합산 가중치와 기존 수량 범위는 유지했다.
- 여름·가을·겨울 행사는 기존 상품과 제조 경로를 사용한다. 행사 자체가 제조법을 자동 학습시키지 않는다. 미학습 제조법은 기존 진행에서 확보한다.
- 계절 판매 행사의 추가 상품 요청은 새로운 고객·군중·건물·날씨·갈증·추위·회복 기능을 만들지 않는다. 겨울 손난로 판매가 플레이어의 난방 능력치를 바꾼다고 설명하지 않는다.
- 새 행사에 방문객 총량 증가를 따로 추가하지 않았다. 기존 방문 손님이 해당 상품을 더 자주 찾는다. 기존 던전·길손·봄 장터 방문 비중 수정은 유지한다.

## 일정과 반복: 조정 가능한 초기 설정

| 행사 | 소문 시점 | 수요 기간 | 반복 |
|---|---|---|---|
| 던전 공략 | 주기 2~3일 | 주기 4~6일 | 28일마다 |
| 길손 여행 준비 | 주기 18~21일 | 주기 22~24일 | 28일마다 |
| 봄 장터 | 봄 8~12일 | 봄 15~19일 | 매년 봄 |
| 여름 길목의 쉼 | 여름 4~7일 | 여름 8~12일 | 매년 여름 |
| 가을 먹거리 나눔 | 가을 8~11일 | 가을 12~16일 | 매년 가을 |
| 겨울 밤길의 온기 | 겨울 11~14일 | 겨울 15~19일 | 매년 겨울 |

정확한 날짜 표는 개발/밸런스 조정용이다. 게임 소문과 메모에는 날짜 범위·판매 배율 공지를 표시하지 않고, 내일/한창/오늘 마무리 같은 생활 시점으로 안내한다. 기존 달력은 계절당 28일, 한 해 112일이다.

- `data/shop/events/store_events.csv`: `event_kind=common|seasonal`, `season_id`, `repeat_days`를 추가했다. 공용 주기는 CSV에서 바꿀 수 있으며 0이면 기존 경과 일자 기준 일회성 행사다. 계절은 계절 안의 일자를 쓰며 매년 반복한다.
- `store_event_demands.csv`: 상품별 추가 가중치·구매 수량. 이번 새 계절 수치는 조정 가능한 초기값이며 Claude 검토 대상이다.
- `StoreEventSchedule`: 원본 설정을 실제 경과 일자와 회차로 변환한다. 계절 밖 수요, 반복 주기를 넘는 공용 기간, 계절 28일을 넘는 기간과 제3의 종류를 거부한다.
- `StoreEventData.get_event()`는 원본 설정, `get_event_occurrence(id, day)`는 해당 시점 회차의 절대 일자다. 활성 수요·방문 비중·소문은 동일 회차 계산을 사용한다.
- 공용/계절 행사가 겹치면 각 추가 수요가 함께 적용된다. 현재 초기 일정은 기간을 나눠 시작한다.

## 소문·저장·기억

같은 회차 소문은 중복 전달하지 않는다. 다음 주기/해에는 다시 소문을 들을 수 있다. 기존 `id → 최근 소문을 들은 경과 일자` 저장 형식을 유지하고 새 회차에서 날짜만 갱신해 기존 신호를 보낸다. 큰 `game_state.gd`는 수정하지 않았다.

대분류 소문은 실제 소분류 손님에게도 전달된다(예: traveler 소문 → backpacker). 만료된 소문을 가진 손님이 늦게 E로 말을 걸어도 이미 끝난 행사를 새 준비 소문으로 전달하지 않는다.

일정 탭은 공용/계절 두 묶음으로 나누고 계절 이름을 표시한다. 소문을 다시 듣기 전에는 마지막으로 들은 회차의 기억과 **그 회차 기간의 실제 전체 매장 영업 기록**을 읽는다. 다음 회차를 들으면 해당 카드가 새 준비 이야기로 바뀐다. 행사 때문에 생긴 매출만 따로 계산했다고 주장하지 않는다.

카드는 행사마다 최근에 들은 회차 하나를 유지한다. 이전 회차 전체 영업 기록은 기존 영업 기록 탭에 남지만, 매년의 소문 카드를 모두 별도로 쌓는 기능은 없다. 소문을 못 들었어도 기간의 실제 수요는 적용된다.

## Gemini가 다듬을 글

기존 service_text에 여름/가을/겨울 18장면 추가, 총 매장 장면 36개, 전체 글 CSV 145행. 이벤트 수와 대사 행 수는 다르다. 기존 봄 장터의 품목 단서도 빵·열매 주스에 맞췄다. API 호출·인물 기준 파일 수정 없음.

기존 세 행사 명령은 이전 문서를 사용하되 최신 Resource/CSV를 읽는다. 신규 세 행사 명령:

```bat
dev\gemini\run_request_text.bat draft service_text --ids store_summer_rumor,store_summer_ongoing,store_summer_closing,store_summer_finished,store_summer_bought,store_summer_missing
dev\gemini\run_request_text.bat draft service_text --ids store_autumn_rumor,store_autumn_ongoing,store_autumn_closing,store_autumn_finished,store_autumn_bought,store_autumn_missing
dev\gemini\run_request_text.bat draft service_text --ids store_winter_rumor,store_winter_ongoing,store_winter_closing,store_winter_finished,store_winter_bought,store_winter_missing
```

실제 품목 이름 토큰 `{item}`, 준비 품목·재료·진열 안내, 반복 구분과 실제 적용 맥락을 유지한다. 가중치·판매 보장 공지나 없는 현장 연출을 대사에 추가하지 않는다.
