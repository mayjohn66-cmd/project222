## 소문·저장·기억

같은 회차 소문은 중복 전달하지 않는다. 다음 주기/해에는 다시 소문을 들을 수 있다. 기존 `id → 최근 소문을 들은 경과 일자` 저장 형식을 유지하고 새 회차에서 날짜만 갱신해 기존 신호를 보낸다. 큰 `game_state.gd`는 수정하지 않았다.

대분류 소문은 실제 소분류 손님에게도 전달된다(예: traveler 소문 → backpacker). 만료된 소문을 가진 손님이 늦게 E로 말을 걸어도 이미 끝난 행사를 새 준비 소문으로 전달하지 않는다.

일정 탭은 공용/계절 두 묶음으로 나누고 계절 이름을 표시한다. 소문을 다시 듣기 전에는 마지막으로 들은 회차의 기억과 **그 회차 기간의 실제 전체 매장 영업 기록**을 읽는다. 다음 회차를 들으면 해당 카드가 새 준비 이야기로 바뀐다. 행사 때문에 생긴 매출만 따로 계산했다고 주장하지 않는다.

카드는 행사마다 최근에 들은 회차 하나를 유지한다. 이전 회차 전체 영업 기록은 기존 영업 기록 탭에 남지만, 매년의 소문 카드를 모두 별도로 쌓는 기능은 없다. 소문을 못 들었어도 기간의 실제 수요는 적용된다.

## 이번 추가 5개의 접근과 초기 수치

도시락·느린 오후·저녁 채비·아침 식탁·감사 인사라는 생활 사정을 서로 다른 상품 수요에 연결했다. 소문, 진행, 마지막 날, 지난 기억, 실제 결제, 실제 무재고의 여섯 장면을 각각 사용한다. 가을 발광 등불은 기존 판매 상품이며 길목 등불 공동 부탁이나 설치 시설과 구별한다. 겨울 아침 이야기는 다음 끼니를 미리 사는 이유이며 구매 가능 시간을 아침으로 제한하지 않는다.

|---|---|---|---|
| 작은 감사 꾸러미 | 60 / 60 | 30 / 30 | 말린 열매 1~2 / 은 펜던트 1 |
| 봄길의 도시락 | 90 / 90 | 45 / 45 | 약초 빵 1~2 / 말린 열매 1~2 |

| 가을 등불 준비 | 90 / 90 | 45 / 45 | 발광 등불 1 / 갈대 차 1~2 |
| 겨울 아침의 식탁 | 90 / 90 | 45 / 45 | 약초 빵 1~2 / 여행자 스튜 1~2 |

두 고객 대분류의 기존 소분류에 적용한다. child 등 다른 대분류의 기본 수요는 유지한다. 신규 행사에는 별도 방문 비중 배율을 추가하지 않았다. 구매 확률·매출 확정값이 아닌 기존 수요 후보에 더하는 가중치이며 Claude 검토 전 초기값이다.

제조법은 기존 두루마리 경로로 배운다. 숲의 말린 열매·약초 빵, 광산의 미네랄 워터·은 펜던트, 늪의 갈대 차·발광 등불, 숲/늪의 여행자 스튜가 대상이다. 은 펜던트는 난이도 2, 발광 등불은 난이도 3, 여행자 스튜는 난이도 2 경로여서 초반에는 준비하지 못할 수 있다. 소문은 자동 학습이나 원정 강제를 약속하지 않고, 제조법을 아는 경우 재료 준비를 안내한다. 미준비 시에는 기존 품절 기록과 짧은 말이 남으며 별도 퀘스트 실패·답례 손실·평판 차감은 없다. 첫해에 모든 상품을 제조하도록 요구하지 않는다.

새 기간은 기존 행사 사이에 넣었다. 소문 기간은 겹칠 수 있지만 현재 구매 수요 기간 사이에는 평소 영업일을 남긴다. 공동 부탁·주민 친밀도·시설·보상·이미지를 추가하는 작업은 포함하지 않는다.

## Gemini가 다듬을 글

기존 service_text에 새 행사 5개의 30장면을 추가했다. 매장 행사만 총 66장면이다. 이후 `docs/콘텐츠/2막/매장_행사에서_이어지는_부탁.md`의 부탁/후일담 10행을 더해 최신 전체 글 CSV는 185행이다(행사 추가 당시 175행). 이벤트 수와 대사 행 수는 다르다. API 호출·인물 기준 파일 수정 없음.

최초 세 행사 명령은 이전 문서를 사용하되 최신 Resource/CSV를 읽는다. 앞서 추가한 여름·가을·겨울 행사 명령:

```bat
dev\gemini\run_request_text.bat draft service_text --ids store_summer_rumor,store_summer_ongoing,store_summer_closing,store_summer_finished,store_summer_bought,store_summer_missing
dev\gemini\run_request_text.bat draft service_text --ids store_autumn_rumor,store_autumn_ongoing,store_autumn_closing,store_autumn_finished,store_autumn_bought,store_autumn_missing
dev\gemini\run_request_text.bat draft service_text --ids store_winter_rumor,store_winter_ongoing,store_winter_closing,store_winter_finished,store_winter_bought,store_winter_missing
```

실제 품목 이름 토큰 `{item}`, 준비 품목·재료·진열 안내, 반복 구분과 실제 적용 맥락을 유지한다. 가중치·판매 보장 공지나 없는 현장 연출을 대사에 추가하지 않는다.

진행 중인 행사에 맞춰 매장 안쪽 두 벽(북·서)에 장식이 걸린다. 바닥에 놓는 물건이 아니라서 진열대·동선과 겹치지 않고, 행사가 끝나면 사라진다.

- 데이터: `data/shop/events/store_event_decor_3d.csv`(행사 id → 장식 종류 `bunting` 깃발 줄 / `garland` 꽃 줄 / `lanterns` 등불 / `lights` 전구 줄, 색, 줄 번호). 행사가 둘 이상이면 줄이 아래로 겹쳐 걸린다.
- 구현: `script/world/view3d/store_event_decor_3d.gd`(`StoreView3D`가 0.25초마다 확인). 확인용: `dev/spike3d/event_decor_shot.tscn`(행사 날짜별 화면 저장).
- 색과 장식 종류는 임시 값이다. 계절 분위기에 맞춘 초안이며 바꾸려면 CSV만 고친다.
