# NPC가 손님으로 들어와 퀘스트를 주는 방식 (제안 초안)

2026-10-12 사용자 제안: 초반 원정 부탁 뒤로는, 해당 NPC가 **손님으로 입장하면서 자연스럽게 퀘스트를 주는** 방식으로 하고 싶다. 상태: ✅ **구현됨(2026-10-13)** — 7장 시험판(부탁 1개) → 8장 전체 확장. 8장 "아직 아닌 것"과 PC 확인이 남았다. ❓는 사용자가 정할 것.

## 1. 지금은 퀘스트가 어떻게 주어지나 (확인한 것)

| 방식 | 어디 | 어떻게 보이나 |
|---|---|---|
| ① 서 있는 NPC | `ResidentRequestDirector`(주민 부탁·소개), `TutorialDirector`(튜토리얼 타블렌) | 가게 안 빈자리에 `StoryNpc`가 나타나 `[E]`로 대화. 손님이 아니다 |
| ② 마을 게시판 곁 | `RegularCustomerDirector`(단골), 게시판·장터 계열 | 게시판 근처에 NPC가 서 있고 `[E]` |
| ③ **손님으로 쇼핑** | `customer_spawner.gd`의 `prepare()` 계열(`RegularCustomerVisits`, `ActFourVisits`, `ExpeditionContactVisits`, `WeatherLifeVisits`) | 행인이 도로 → 문 → 진열대 → 계산대를 따라 **실제 손님으로** 쇼핑하고 이름표가 붙는다. 대화는 안 하거나 결제 직후 짧은 한마디 |
| ④ **손님으로 입장해 대화** | `CheckoutTutorial`(델빈) | 문 앞에서 소개 대사 → 계산대에서 결제 대사 → 결제 뒤 마무리 대사. 이때 일반 손님 생성을 멈추고 플레이어를 계산 자리에 세운다 |

→ 사용자가 원하는 모양은 **④의 방식을 튜토리얼 밖의 퀘스트 전반으로 일반화**한 것이다. ③의 태그 방식(`prepare`)으로 "이 손님이 이 이야기의 주인"임을 정하고, ④의 대화 방식으로 퀘스트를 건넨다.

## 2. 제안: "의뢰 손님(QuestVisit)"

한 번의 방문은 이렇게 흐른다.

1. **예약**: 이야기 흐름이 "지금 이 NPC가 퀘스트를 줄 차례"라고 알린다(조건은 기존 흐름이 이미 계산한다: `ResidentRequestFlow.current()` 등).
2. **입장**: `customer_spawner`가 일반 손님 대신 그 NPC 종류(`customer_type_id`)의 손님을 한 명 만든다. 이름표 + 퀘스트 표시. 도로 → 문 → 진열대까지는 일반 손님과 같다.
3. **대화**: 계산대에 도착하면(결제 전) 플레이어에게 퀘스트를 건넨다(소개 → 부탁 → 받아들이기). 대화 중에는 시간·이동을 멈춘다(`CheckoutTutorial`과 같은 복원 처리).
4. **결제와 퇴장**: 평소처럼 결제하고 나간다. 퀘스트는 수락 기록이 남아 수첩에 표시된다.
5. **전달·보고**: 재료를 가져오면 **다시 손님으로 입장**해 받아 간다(또는 다음 방문 때 완료 대사). ❓

**필요한 새 부품**
- `QuestVisits.prepare(customer, introduced_type)`: 기존 `prepare` 줄(`customer_spawner.gd` 217~224행 근처)에 한 줄 추가.
- 계산대 대화 진행기: `CheckoutTutorial`의 단계 진행(`intro → checkout → finished`)을 퀘스트용으로 일반화한 새 파일. 튜토리얼 코드에 덧붙이지 않고 따로 만든다.
- 각 퀘스트 흐름(`resident_request_flow` 등)에서 "NPC를 세우는" 부분을 "의뢰 손님을 예약"으로 바꾼다.

## 3. 그대로 둘 것과 바꿀 것

- **바꾼다**: 주민 부탁·소개(①)를 가장 먼저. 이미 "손님이 찾아와 인사한다"는 문구가 있다(`ResidentRequestDirector`의 "가게를 찾은 손님과 인사하세요").
- **그대로 둔다(제안)**: 게시판 곁 단골(②)·장터·낚시 선생 같은 **마을 쪽 대화**는 NPC가 마을에 사는 사람이라 서 있는 방식이 자연스럽다.
- **초반 타블렌의 원정 부탁(오늘 구현)**: 지금은 `StoryNpc`가 가게 안에 나타난다. 이것도 손님으로 입장하게 바꿀지 ❓.

## 4. 위험과 확인할 것

- `customer.gd`(2,075줄)와 `register`·계산 처리에 손을 대야 할 수 있다. 새 기능은 큰 파일에 덧붙이지 않는 규칙이라, 계산대 도착 알림을 받는 얇은 연결만 만들고 나머지는 새 파일에 둔다.
- 영업 중이 아니거나 진열대가 비어 있으면 손님이 입장하지 않는다 → 퀘스트가 영영 안 나온다. **대체 경로**(게시판·서 있는 NPC)를 둘지 정해야 한다.
- 일반 손님이 많아 계산대가 붐비면 대화가 밀린다. 의뢰 손님은 줄 맨 앞으로 모시거나 한가할 때 입장시켜야 한다.
- 직원이 계산하는 시간에는 플레이어가 계산대에 없다. 대화는 플레이어가 계산 자리에 있을 때만 시작해야 한다(`CheckoutTutorial`은 계산 자리를 예약한다).
- 기존 테스트는 서 있는 NPC를 가정한 것이 많다(`check_resident_*`, `check_progressive_tutorial`, `check_village_journal` 등). 한 흐름씩 바꾸며 갱신해야 한다.
- 게임을 실행해서 걷는 손님·대화 타이밍을 눈으로 확인하지 못한다. 구현 뒤에는 PC에서 보셔야 한다.

## 5. 사용자가 정할 것 ❓

1. 범위: 주민 부탁·소개부터 / 튜토리얼 타블렌도 포함 / 전부
2. 대화 시점: **결제 전**(계산대에 서자마자) / 결제 뒤
3. 입장하지 못할 때(영업 중 아님·재고 없음): 서 있는 NPC로 **대체**할지, 그냥 기다릴지
4. 전달·보고도 손님 입장으로 할지, 한 번 받은 퀘스트는 게시판·NPC에게 직접 가서 내는 현재 방식을 둘지

## 6. 제안 순서

1. 계산대 대화 진행기와 `QuestVisits.prepare`를 새 파일로 만든다(주민 한 명 분량).
2. 타블렌의 `settle_naru` 같은 주민 부탁 하나로 시험한다(재고 있음 → 입장 → 계산대 대화 → 결제 → 수락).
3. 테스트를 만들고 PC에서 눈으로 확인받는다.
4. 나머지 주민·소개를 옮긴다.

## 7. 시험판 구현 (2026-10-12) — 첫 주민 부탁 `neighbor_bread`(이웃 오렐) 하나

사용자 지시: "주민 부탁 하나로 먼저 시험". 5장 ❓ 중 사용자가 정하지 않은 것은 제 권장안으로 두었다(아래 표시).

**흐름**: 영업 중(개점 상태) 부탁 차례가 되면 오렐이 문으로 들어옴 → **문 앞에서 부탁 대사**(기존 부탁 글 `lines`) → 끝까지 들으면 **수락 기록** → 진열대에서 상품을 하나 골라 계산대로 → **플레이어가 실제로 계산** → 결제 직후 "필요한 물건은 …개야" 안내 → 퇴장.

| 항목 | 시험판의 선택 |
|---|---|
| 범위 | `data/shop/requests/quest_visits.csv`에 적은 부탁만(지금은 `neighbor_bread` 한 줄). 줄을 추가하면 다른 주민 부탁도 같은 방식으로 간다 |
| 대화 시점(2번) | 입장 직후 문 앞 + 결제 뒤 안내(튜토리얼 델빈과 같은 모양). 권장안과 다르게 "결제 전"이 아니라 "입장 직후"다 |
| 입장 못 할 때(3번) | **서 있는 NPC가 대체**. 영업 전·후나 진열 상품·계산대·문이 없으면 기존 NPC가 그대로 말을 건다. 영업 중에는 서 있는 NPC가 사라지고 손님으로 온다 |
| 전달·보고(4번) | 그대로(수락된 부탁은 서 있는 NPC에게 `[E]`로 전달). 이번 시험 범위 밖 |

**새 파일**: `script/world/shop/requests/quest_visit_director.gd`(`QuestVisitDirector`, 월드 씬 `main.tscn`에 노드 추가), `data/shop/requests/quest_visits.csv`, 테스트 `dev/script/check_quest_visit.gd`. **바꾼 파일**: `resident_request_director.gd`(영업 중에는 서 있는 NPC를 치우는 7줄). 튜토리얼 코드(`CheckoutTutorial`)와 `customer.gd`는 건드리지 않았다. 안내 손님(`CheckoutGuideCustomer`)을 그대로 쓴다.

**알려진 한계**
- 안내 손님 모습은 튜토리얼 델빈과 같은 "마을 사람" 모양이고, 이름표만 오렐로 바꿨다. NPC별 겉모습은 아직 아니다.
- 입장 중에는 일반 손님 생성이 멈춘다(튜토리얼과 같은 방식). 일반 손님이 많을 때 계산대가 비어 있어야 시작된다.
- 직원이 계산대를 맡는 시간대에는 시작하지 않는다(계산 자리 예약 실패). 플레이어가 계산대를 쓸 수 있어야 한다.
- 영업을 시작하자마자 시작되지 않을 수 있다(1초마다 확인).

**확인한 것**: `check_quest_visit`(20건, 입장 → 대화 → 수락 → 구매 → 결제 → 안내 → 퇴장, 영업 전 대체), 기존 주민 부탁·튜토리얼·마을 수첩·프롤로그·마을 확장 테스트 통과.
**확인하지 못한 것**: 게임을 실행해 걷는 모습·대화 타이밍·계산대 위치를 눈으로 본 것. PC에서 영업을 켜고 첫 주민 부탁 차례에 확인해 주셔야 한다.

## 8. 전체 확장 (2026-10-13) — 최대한 재활용

사용자 지시: "이번 주 목요일 전에 모든 걸 끝내야 하니 최대한 재활용하자. 다른 부탁들도 전부 이런 방식으로."

**재활용의 핵심**: 각 감독이 이미 가진 대화·보상·기록 처리를 그대로 쓴다. 감독마다 공통 함수 3개만 내놓는다.
- `visit_target()` — 지금 건넬 이야기가 있는 대상 `{id, key, name, standing}` 또는 `{}`
- `begin_visit(id)` — 거리·보이는지와 상관없이 그 대상과의 대화를 원래 방식으로 연다
- `visit_busy()` — 대화(또는 패널)가 열려 있는 동안 true

`QuestVisitDirector`가 이 함수를 가진 감독을 찾아 대상을 문으로 들여보내고, 대화가 끝나면 실제 상품을 계산하게 한 뒤 퇴장시킨다. 한 이야기 대상은 하루에 한 번만 온다.

| 감독 | 포함되는 이야기 | 바꾼 곳 |
|---|---|---|
| `ResidentRequestDirector`(전용 경로) | 주민 부탁 9개(기본 6 + 정착 부탁) — 부탁 수락 | 영업 중 서 있는 NPC 숨김(7줄) |
| `VillageLifeDirector` | 개인 부탁(도윤·나루·소라)·계절 사건·주민 기억·호감·전력 복구·보존 수업·제작 이야기·부탁 뒤 후일담 | 함수 3개 + `nearest()`에 방문 대상 지정 |
| `RegularCustomerDirector`(3개 인스턴스) | 단골 재방문 부탁, 원정에서 만난 사람, 날씨 인사 | 함수 3개 + `near()` |
| `VillageExpansionDirector` | 마을 확장 이야기의 **주민 한 명과의 단계** | 함수 3개 + `nearest()` |
| `ActFourDirector` | 4막 길 위의 이야기(마칠 수 있는 단계) | 함수 3개 + `nearest()` |
| `LanternWayfarerDirector` | 등불 아래의 길손(소개·재료 전달·재방문) | 함수 3개 + `near()` |

**데이터**: `data/shop/requests/quest_visits.csv` 한 줄이 한 묶음이다(`*`, `life:*`, `regular:*`, `expansion:*`, `act4:*`, `lantern`). 줄을 지우면 그 묶음은 원래 서 있는 NPC 방식으로 돌아간다. `life:naru`처럼 개별 주민도 가능하다.

**아직 이 방식이 아닌 것**
- 마을 확장의 **모임(gather) 단계** — 여러 이웃이 한 장소에 모이는 이야기라 한 명이 들어오는 모양이 맞지 않는다.
- **대장간·낚시 선생·스토리 이벤트(`StoryDirector`)·비밀 상인** — 이야기를 건네는 것이 아니라 서비스 창(제작·강화·낚시·구매)이어서 제외했다.
- **튜토리얼 타블렌의 원정 부탁**(오늘 구현한 `expedition` 단계) — 튜토리얼 흐름(`TutorialDirector`)이라 이번에는 건드리지 않았다. 원하면 `ResidentRequestDirector`와 같은 방식으로 옮길 수 있다.
- 부탁을 **받는 것**만 손님으로 하고, 이미 맡은 부탁을 **내는 것**은 감독별 원래 방식이다. 다만 `VillageLifeDirector`·단골·4막·등불 길손은 "전달·후일담" 단계도 같은 대상 함수로 들어와 손님으로 온다. 주민 부탁(`ResidentRequestDirector`)의 전달만 서 있는 NPC가 한다.

**알려진 한계와 위험**
- 걷는 손님·대화 타이밍·계산대 도착은 **실행해서 눈으로 확인하지 못했다.** 테스트는 대화·수락·결제·상태 복원을 확인한다.
- 안내 손님(`CheckoutGuideCustomer`)의 겉모습은 모두 같은 "마을 사람"이고 이름표만 바뀐다.
- 한 번에 한 명만 들어온다(안내 손님이 계산 자리를 예약한다). 대기 중인 이야기가 많으면 하루에 여러 명이 차례로 오는 것이 아니라, 1초마다 확인해 비는 때 한 명씩 온다. 영업 중 일반 손님은 입장 동안 멈춘다.
- 영업 중에만 온다. 영업 전·후에는 기존 서 있는 NPC가 그대로 말을 건다.
- 대화 중 시간이 멈추는 것은 각 감독의 원래 처리를 따른다.
- 테스트는 `check_quest_visit`(주민 부탁 + 마을 주민 이야기 호감 부탁)로 확인했다. 단골·4막·마을 확장·등불 길손은 **공통 함수 3개가 있고 호출되는지까지만** 시험했다. 각각의 실제 방문(입장 → 대화 → 보상)은 시험하지 못했다.
